### A2 — existing ASCII correctness: precision gate before code

The revised raw-brightness direction is preferable to papering over double inversion, but its current wording is insufficient for a shared-particle migration. Source inspection exposes two additional details within the already planned static/fade parity scope:

1. `BaseEffect.getBrightness` uses 0.3/0.59/0.11 while `AsciiRenderer.render` uses 0.2126/0.7152/0.0722. Raw storage alone cannot make colored-scene glyph selection agree.
2. Static ASCII rejects **raw** brightness below threshold, then inverts. Particle initialization thresholds raw brightness and invokes `shouldDraw` with adjusted brightness; ASCII `shouldDraw` applies another threshold and strict `>`. Choose the explicit common rule, not just “exactly once”: preserve current static ASCII raw-luminance threshold (`raw >= minBrightness`, alpha zero excluded), then invert once for glyph/palette mapping. Freeze the ASCII luminance coefficients to the current static coefficients in its sampling path. Other renderers must not silently acquire a new appearance.

Before A2 implementation, record how raw luminance/alpha travels through particles and every fade descriptor into ASCII without changing other renderers' existing adjusted inputs. An additive renderer-specific/raw sample path is acceptable; a shared migration requires regressions for every affected renderer and fade variant. The authoritative plan requires raw luminance+alpha: retain source alpha distinctly from animation opacity and state how partial alpha is composed; do not claim alpha parity merely from skipping zero-alpha samples.

Gate A2 with failing-then-passing colored (not only grayscale) fixtures at brightness endpoints/midpoint, below/equal/above threshold, both inversion settings and palette modes, transparent/partial-alpha cells, all named ramps, nondivisible dimensions and fade→static boundaries. Exercise post-effects without attributing their changes to glyph selection. Compare representative legacy non-ASCII outputs if shared code changes. No custom ramp/font/atlas/edge feature is required. **A1 may proceed without A2; A2 is held until this explicit data-path contract is written and independently checked.**

Custom ramps remain a later CO-R4a delivery with the exact approved repertoire, warning ownership and hydration/editor/SDK/CLI boundary tests. CO-R4b/c remain blocked on face/license/hash, appearance comparisons and measured packaging/transfer approval; this review approves neither a font nor the proposed numeric budget as measured evidence.

## CI safety audit: mandatory edits before deployment

Observed `.github/workflows/ci.yml` still deploys from `check` on main pushes (lines 47–52), without depending on `cli` (53–65). Its embed and CLI steps perform additional `npm install`; root Vitest excludes package and dedicated decode suites. `playwright.config.js` starts Vite dev with `reuseExistingServer: true` and has Chromium-specific launch flags but no second-engine project. These are concrete gaps, not resolved by the revised checklist.

A separately approved CI safety change must implement:

- **Validation/deploy DAG:** remove deployment from `check`; create a production-environment deploy job whose explicit `needs` includes successful root lint/format/tests/build, SDK tests/build/size/alias verification, CLI build/tests, decode suite, and generated-artifact browser validation. Restrict its event/ref to authorized main release execution. No failure-tolerant required jobs, missing-suite success or PR/fork production credentials.
- **Reproducible installs and build identity:** Node 20, committed workspace lock and root `npm ci` in each isolated job; remove later unconstrained workspace installs. Account for CLI's existing prepare hook rather than confusing install-time build with explicit verification. Root `prebuild` already builds/copies the SDK: remove redundant later SDK rebuild or arrange one explicit chain. Hash-compare `packages/embed/dist`, `public/embed`, app output and packaged Embed SDK bytes. Enforce the existing 51,200-byte JS gzip cap and alias check on the exact packaged bytes, plus helper/asset manifests when added.
- **Real missing suites:** invoke `npm test --workspace @bitmapforge/embed`, `npm run build --workspace @bitmapforge/cli`, `npm test --workspace @bitmapforge/cli`, `npm run test:export`, and generated/browser checks in addition to root commands. Install browsers/system dependencies explicitly. Add the missing SDK/React/Web Component lifecycle fixtures as those features land; typography cannot release until two real engines with appropriate flags and DPR coverage run. Timing benchmarks remain informational, not deploy thresholds.
- **Built-artifact browser configuration:** update the test config or add a dedicated release config to serve isolated production output, disable existing-server reuse, assert readiness/revision and execute extracted freshly generated archives. Dev-server tests alone cannot satisfy this job. Cover non-root hosting, correct SDK/model/font/helper bytes/MIME and HTML-with-200/missing-asset failures. Upload traces/screenshots/logs/decode evidence even on failure; no silent skip counts as passing.
- **Verified deployment output:** pin the Vercel/toolchain path. Prefer validated Vercel output and `deploy --prebuilt`; raw `dist` is not automatically Vercel output. If a rebuild is explicitly accepted instead, prove provenance and served asset identity, not just upload `dist` and assume reuse. Deploy only the artifact/revision validated by the prerequisite jobs.
- **Release protection/order:** configure the deploy job's protected environment with required approval for every release, including docs-only changes; keep validations runnable. Add production concurrency and an explicit stale-revision guard/serialized release strategy so old runs cannot overwrite newer production. Merely canceling an in-progress CLI process is not proof a remotely accepted deployment was canceled. Record rollback owner/target.

Workflow YAML alone cannot prove enforcement. Before release, separately authorized readback must confirm required branch checks, environment reviewers/protected branches and production-secret boundaries, plus external Vercel Git integration cannot bypass the workflow. None was inspected remotely here. Postrelease revision/assets/fresh Embed/reduced-motion/visibility smoke and rollback authority require explicit release authorization. **No main push or deployment is approved while these gates remain unresolved**, including a UI-first release that still uses the unsafe production path.
