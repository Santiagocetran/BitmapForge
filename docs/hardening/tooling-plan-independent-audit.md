## Blocking revisions

### R1 — Replace the nonexistent path-targeted npm update interface

**Evidence:** plan line 90 prescribes `npm update --package-lock-only --ignore-scripts --save=false <explicit-package-paths>` and says it resolves named lock paths. npm 11.21.2 accepts **bare package names**, not literal lock paths. Independent read-only inspection of the already cached npm source found:

- `lib/commands/update.js:45,70–72` passes the argument array to Arborist as `update`.
- `node_modules/@npmcli/arborist/lib/arborist/build-ideal-tree.js:243–255` parses each argument and throws `EUPDATEARGS` when `spec.raw !== spec.name`.
- The same file's named-update traversal matches `node.name` across the inventory, not the literal lock location. Its own comment says named packages update wherever they are.
- [Official npm 11 update documentation](https://docs.npmjs.com/cli/v11/commands/npm-update/) documents `npm update [<pkg>...]`, semver-constrained resolution and workspace selection, not a nested package-path selector.

Consequently `node_modules/micromatch/node_modules/picomatch` is not a supported selective update argument. Replacing paths with names does not automatically isolate Zod 4 from the retained BiDi Zod 3 occurrence, or distinguish the two picomatch lines. Workspace selection is not a substitute for consumer-edge selection in the shared root graph.

**Required disposition:**

1. Distinguish the **literal path allowlist used to validate the result** from npm's **package-name inputs**. Supply valid commands with explicit root/workspace participation for root/embed/CLI synchronization.
2. A name-targeted update may be a rejected candidate generator, never a guarantee of path isolation or exact version selection. Keep complete parsed-diff rejection and restore only the isolated operation's candidate snapshot.
3. Retain the temporary-constraint fallback in line 91, but spell out the consumer-scoped overrides for repeated names/major lines and the exact direct constraints. Keep the sole permanent get-uri override unchanged. Do not constrain the BiDi Zod 3 consumer to Zod 4.
4. Specify how temporary constraints are removed and approved final manifest/lock-root/workspace metadata is synchronized without copying arbitrary package records, inventing integrity/resolved fields or accepting a broad refresh. Final `npm ci` and `npm ls` must use the final caret manifests with **no hidden temporary override**. Compare the final lock hash before/after clean installation.
5. If npm cannot produce that final bounded graph, stop for a revised allowlist/strategy and independent acceptance. Do not convert the fallback into permission to hand-patch the lock.

The fallback is reasonable in principle; this review does not assert it has been exercised or that the present command sequence is runnable.

### R3 — Resolve the source-visible generated-project asset/build obstacle explicitly

**Evidence:** `codeExport.js:65–68` emits `fetch('./models/<name>')`; `:80–82` writes the model under top-level `models/`; `:104` emits an empty `defineConfig({})`. The archive has no model asset import/`?url`, no `new URL(..., import.meta.url)` reference, no `public/models/` placement and no copy configuration. A successful dev-server fetch of a project-root file does not mean Vite will copy it into `dist`.

[Official Vite asset documentation](https://vite.dev/guide/assets.html) distinguishes imported asset-graph emission from `public/` assets copied verbatim. An ordinary runtime `fetch` string is not that asset graph. Therefore the required generated project's `npm run build` may succeed while preview fails to fetch its model and renders no geometry. This is a **source-grounded expected baseline defect**, not an executed reproduction and not a candidate regression claim.

Plan lines 124–128 correctly demand baseline reproduction, unmodified fresh ZIP bytes, consumer installation, build, preview, dev, dimensions/resizing, meaningful pixels and no failed runtime requests. Preserve all of them. However, lines 25/53 permit only a generated Vite-floor change and its manifest assertion, with all other generated behavior unchanged. A model-copy/runtime remedy is not covered by that floor-only authorization.

**Required disposition:** name this expected obstacle before implementation; require the baseline gate to inspect the generated `dist` model file/request and retain its failure independently from the install/build exits. Either obtain an independently accepted narrow prerequisite/amendment for generated-project asset packaging (including regression coverage and an explicit archive-layout/static-host compatibility decision), or state B completion is blocked pending that separate repair. Do not copy the model into `dist`, inject an import map, patch the extracted runtime, serve project-root files alongside `dist`, or count dev-server success as the production-preview pass. Do not silently broaden the two-file source permission into a packaging repair.
