## Publication architecture options

Official Vercel docs retrieved for this decision:

1. [Build Output API](https://vercel.com/docs/build-output-api), [configuration](https://vercel.com/docs/build-output-api/configuration), [static primitives](https://vercel.com/docs/build-output-api/primitives): `.vercel/output/config.json` requires version 3; public files belong under `.vercel/output/static` and their contents/names are preserved. Routes, headers and content-type overrides are separate configuration.
2. [CLI build](https://vercel.com/docs/cli/build), [pull](https://vercel.com/docs/cli/pull), [deploy](https://vercel.com/docs/cli/deploy): `vercel build --prod` produces Build Output API output; `--prebuilt` consumes that output, not raw Vite `dist`. `pull` downloads project settings **and environment variable values** into `.vercel/`; do not run it during this audit or upload that whole directory. Prebuilt builds need explicit handling of build-time system variables. Deploy metadata cannot change already embedded values.
3. [Promote](https://vercel.com/docs/cli/promote), [rollback](https://vercel.com/docs/cli/rollback), [Instant Rollback](https://vercel.com/docs/instant-rollback): production-target deploy with `--skip-domain` can be verified before separate promotion. A Preview build is not automatically the same production-configured artifact; current docs warn that promoting Preview creates a new production deployment. Rollback eligibility depends on prior production aliasing, plan and permissions.

These are current documentation capabilities, not a local compatibility test of pinned CLI 65.15.0. Validate the exact selected flags/version in the independently reviewed implementation; do not silently upgrade the CLI.

## Rollback verification contract

**Not exercised by this audit.** Before any production transition, the release owner must name the rollback operator and an eligible **immutable deployment ID/URL**, retain its source revision, complete expected public hashes/config and domain mapping, and confirm access and retention. Do not assume the previous Git SHA can be rebuilt identically or that all older deployments are eligible. Current Vercel docs limit Hobby rollback to the immediately previous production deployment; Pro/Enterprise permit eligible older production targets. Confirm actual plan, role and target instead of assuming either.

- Before release: read provider target state and smoke/hash the known-good immutable URL without changing aliases; verify project domains and any custom aliases, dependencies and old build-time configuration remain valid. Record operator contact and evidence location. A staged candidate never aliased to production is not automatically an Instant Rollback target.
- On incident, with incident/release authorization: coordinate all writers and pending promotions; use provider rollback to the recorded eligible target (or an explicitly approved promotion recovery path). A failed/canceled CLI or timeout does not establish the provider operation stopped. Poll status and read actual deployment/domain state; account for one-at-a-time rollback/promotion jobs and possible conflicts.
- After rollback: verify public alias points to that exact target, all expected public bytes/MIME and representative load/export/Embed flows pass, and document the result. Do not claim recovery from HTTP 200 or a successful command alone. A rollback drill itself is a production change and is not authorized here; rehearse elsewhere or schedule a separate owner-approved window.
- Vercel documents that rollback disables automatic domain assignment; promotion to undo it re-enables assignment. Read that state back and ensure unrelated Git deployments cannot overwrite recovery. Resuming forward releases requires a newly verified/approved candidate, explicit owner decision and the same gates. Returning to an old source-based workflow is not itself rollback of the deployed artifact.
