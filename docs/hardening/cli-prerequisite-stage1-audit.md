## Required stage-1 revisions

### R1 — medium: outer legacy test expires before its containment deadline can finish

**References:** `packages/cli/src/__tests__/cli.test.js:276–307`; `packages/cli/src/__tests__/cli-integration-helpers.js:24,33–41,60–69`.

P11 invokes `runChild` with its default **60-second child deadline**, but the enclosing Vitest test also has a **60-second timeout**. The helper deliberately continues after its deadline to TERM, allow five seconds, KILL if necessary, await child close and poll group disappearance. Thus a hung child reaches the runner timeout before containment/evidence completion. The awaiting test/finally and its temporary-directory cleanup can outlive the test, and runner shutdown can interrupt containment. This is a test-lifetime defect, not an application cancellation defect. The before-P test already had a 60-second outer timeout; the newly introduced deadline must now be composed correctly with it.

**Independent bounded reproduction:** invoked the delivered helper with `deadlineMs:300` against a benign Node child that ignores TERM. Actual result: PID `2386025`, `signal:SIGKILL`, `failure:"deadline exceeded"`, `elapsedMs:5327`, `emergencyReap:true`, `groupAlive:false`. This proves helper completion necessarily extends beyond the child deadline; it does not claim the 60-second browser path was executed.

**Correction:** retain the accepted 60-second render deadline and five-second TERM grace; give the enclosing test an explicit larger containment/finalization envelope, with a documented bound and teardown margin (for example 80 seconds). Do not increase the render deadline or turn timeout into success. Add a short-deadline TERM-resistant child regression that awaits KILL/close and checks failure, emergency reap and absent owned group. Apply the same layered budget rule to stage-2 integration tests. If the owner freezes a 60-second _total_ test budget instead, obtain an explicit budget disposition rather than silently shortening P's accepted child deadline.

### R2 — medium: claimed fail-fast regression cannot detect continuing after the failure

**References:** `packages/cli/src/__tests__/cli-cleanup.test.js:5,110–119`; accepted P plan §5, paragraph following P11.

The injected order is `a.bforge`, `b.bitmapforge`, `notes.txt`. The test fails reading b and checks a/b reads and one write. There is **no later supported project**, so a regression that records b's error but continues to subsequent supported inputs would still satisfy this test. The accepted requirement explicitly calls for valid → failure → later-not-started; a filtered text file cannot be the last leg. Production `index.js:97–100` currently awaits sequential render and is fail-fast; this finding concerns missing regression protection, not a proven production batch bug.

**Correction:** explicitly set the case's entries to a valid first project, failing second project, and supported third project (plus optional ignored text). Assert no third read/launch/write, one completed first artifact/path, nonzero exit, and cleanup completion. Reset the mutable entry list per test to avoid cross-test contamination. Demonstrate that a continue-after-error mutation fails this assertion. Preserve all historical assertions and directory-order independence of the real batch ledger.
