## 2. Source trace and editor comparison (static facts)

### Parser and settings

`index.js:18–63,104–130` reads raw project JSON and passes CLI format/fps/width/height to the page. `projectParser.js:6–16` reads nested `settings`, embedded `model`, and nested `inputType` (default model); version 1 migration adds defaults. Frozen v2 fixtures use the actual nested contract, cube `size:2`, or self-contained asymmetric tetrahedron OBJ, explicit background/palette/pixel size/seed, fade disabled, speed 3 and only spinY enabled. Parser does not map those settings to camera or model transforms.

`harness.js:182–223` constructs SceneManager with spread settings, sets size, loads content, calls `setRenderMode`, then animation/effect updates. It does not call `setLightDirection`, `setBaseRotation` or `setModelScale`. Editor `PreviewCanvas.jsx:26–59,135–171` explicitly initializes animation/light/base pose/active scale/render mode, sizes immediately and via ResizeObserver, then loads source in a later effect. Editor uses store selectors/defaults rather than treating every project field as an effect option. Missing CLI application of optional pose/light/scale is a parity seam, not demonstrated cause for these fixtures (which do not specify them). `fadeMode` is selected by the editor but omitted by SceneManager's forwarding method; it is shared preexisting behavior, outside this no-fade fixture diagnosis.

Frozen token `bayer4` is not `bayer4x4`. BitmapRenderer tolerates it through fallback/threshold paths (`BitmapRenderer.js:71–81,104–128`). Preserve it literally; these artifacts do not certify Bayer-4x4. Do not normalize it to obtain a pass.

### Geometry and camera

`SceneManager.js:28–53` creates perspective camera fov75/aspect1/near0.1/far1000 at `(0,0.5,5)` looking at origin and fixed lights. `setSize:194–201` updates aspect/projection and effect size; there is no camera auto-fit here. `shapeGenerator.js:25–61` creates a cube mesh; `modelLoader.js:18–37,54–98` loads OBJ, assigns white materials/normals and centers/scales longest extent to 3. `_commitSource:129–149` installs source under animGroup/baseGroup and starts fadeIn **even when animation settings will subsequently disable fading**. Actual runtime finite bounds, mesh presence, clip visibility, transforms and camera matrices remain unmeasured by the stage-2 observer. No evidence currently warrants moving the camera or changing geometry/materials.

### Sizing, renderer lifetime and capture — strongest lead

`SceneManager.setSize` → `BitmapEffect.setSize:99–106` → `BaseEffect.setSize:37–42` sizes WebGL, sample grid and active 2D output. CLI explicitly calls this, so CSS-only sizing is not an established defect. The harness comment that DPR is hardcoded to 1 is not enforcement: SceneManager uses `min(window.devicePixelRatio || 1,2)`; actual DPR/backing dimensions need measurement, not a policy change.

`SceneManager.setRenderMode:275–279` creates a renderer even for the current mode. `BitmapEffect.setRenderer:76–82` queues it while a fade is active. At capture, `seekTo` with fade disabled sets phase `show`/`isAnimating=false`; `renderBitmap:130–133` can then `_swapRenderer`. `_swapRenderer:84–96` disposes/removes the previous renderer's canvas and initializes a new one. `getCanvas:289–294` returns the **current active** canvas, not a stable lifetime handle.

Both CLI capture paths cache `const sourceCanvas = manager.getCanvas()` **before** their first `renderAtTime` (`harness.js:31–54,73–85,135–139`). A pending swap at that first render could leave captures reading a detached, stale canvas throughout the loop. This sequence is visible in source; its occurrence/timing and causal responsibility in recorded artifacts are **not yet observed**. It can plausibly explain correct capture times with unchanging pixels, and shape/model differences caused by intervening async load/live frames. Do not present that explanation as a confirmed root cause.

The working editor reference initializes render mode before source load; the CLI does so after load starts fade. Editor exports `framesProvider.js:26–52` also cache a canvas before stepping. Thus the shared export helper is not inherently safe against a pending swap either. Do not copy the helper or reorder CLI calls blindly; measure both sequence and canvas lifetime. This assignment did not rerun or independently certify a working editor artifact at these exact settings.

### Scheduling and encoding

`AnimationEngine.js:327–335,348–449` computes duration and seeks absolute transform/phase. `SceneManager.renderAtTime` seeks then renders synchronously. Harness APNG uses `max(12,round(loopSeconds*fps))`, time `i*loopMs/frameCount`, rounds delay `1000/fps`, yields every four frames and resumes in finally. This mirrors editor framesProvider (excluding editor cancellation/progress). WebM renders the same times, draws to its even-sized capture canvas and waits `loopMs/frameCount` between steps. APNG copies ImageData bytes before UPNG; WebM uses real captureStream/MediaRecorder. Existing scheduling observations argue against missing calls, but do not rule out stale source canvases, stale transforms, an effect-stage collapse or encoder divergence.
